## What the shell does

After boot checks and `hello world`, `minemu_kernel_main` turns on the UART0 receive interrupt, unmasks that source in the interrupt controller, enables CPU IRQs, and enters the shell.

`msh` prints `msh> ` and reads until `\n`:

- Leading spaces are skipped. An empty or all-space line prints the prompt again.
- The line holds 20 bytes, not counting the newline. A 21st byte latches overflow: the rest of the line is dropped and not executed.
- `0x08` and `0x7f` delete one stored byte. Either one on an empty line is ignored.
- `echo TEXT` prints `TEXT` and a newline. Spaces right after `echo` count as one separator. `echo` alone prints a blank line.
- Any other word prints `command not found: COMMAND`.

Typed characters are not written back to UART. The emulator already mirrors them.

## Interrupts

`kernel/src/startup/irq.S` is the context-switch example’s trampoline: it builds the 88-byte trap frame, reads the controller `claim` register, calls `minemu_irq_dispatch`, and returns with `subs pc, lr, #4`. A `nop` sits after the user-register restore so that access is not the next instruction.

`minemu_irq_dispatch` calls a four-entry handler table, writes that source id to `eoi`, and returns the same frame. The UART0 handler reads every ready `rx_data` byte into a 128-byte queue before `eoi`, so the interrupt does not fire again immediately.

The shell pops that queue with IRQs masked, then unmasks. The handler itself does not unmask: the CPU already did that on IRQ entry.

## UART driver API

The driver is in `kernel/include/minemu/uart.h` and `kernel/src/runtime/uart.c`. It has two layers, because transmit and receive have different constraints.

The transmit and polled-receive calls take a `volatile struct minemu_uart_regs *`. UART0 and UART1 have the same register layout, so one implementation serves both. The console passes `MINEMU_UART0` because that is the port attached to the emulator console. Every access goes through that struct, so the compiler emits one aligned 32-bit load or store. A byte access, or a read of `tx_data`, or a write of `rx_data`, would be a data abort.

- `minemu_uart_putc` waits until `STATUS.TX_READY` is set, then writes the byte in bits `[7:0]` with the upper bits clear.
- `minemu_uart_write` sends a counted buffer and does not look for a terminator.
- `minemu_uart_puts` sends bytes up to a NUL and adds no newline. A NULL pointer is ignored.
- `minemu_uart_getc` does not wait. It returns `-1` when `RX_READY` is clear, and otherwise returns the oldest byte as an `int`, so a stored `0x00` is distinct from "nothing available."

There is no software transmit queue. Under this device, `TX_READY` stays set and each write is accepted immediately, so a poll-and-store matches the hardware and keeps the send path correct if a later device can stall.

Receive after startup does not use `minemu_uart_getc`. Once the RX interrupt is on, the interrupt handler owns the hardware FIFO. A second reader of `rx_data` would steal bytes from that handler. The interrupt path is therefore a separate UART0 API:

- `minemu_uart0_rx_open` clears the software queue and sets `CONTROL` bit 0, which enables the RX interrupt.
- `minemu_uart0_rx_isr` is the handler the IRQ table calls for source `MINEMU_IRQ_UART0`.
- `minemu_uart0_rx_wait` blocks until the software queue has a byte, then returns it.

The shell calls only `minemu_uart0_rx_wait`. Printing stays on the polled transmit functions, through `minemu_putc` and `minemu_puts`. Transmit never enables an interrupt, so logging from the shell does not re-enter the driver.

## Shared state

The shared object is one static queue, `uart0_rx`, of 128 bytes, with a head index, a tail index, and a count. The interrupt handler is the only producer. `minemu_uart0_rx_wait` is the only consumer. The queue is `volatile` so both sides reload the indexes and the count.

The handler runs with IRQs already masked by the CPU. It reads `rx_data` while `RX_READY` is set and pushes each byte. It does not call `minemu_irq_enable`. Unmasking inside the handler would allow a nested IRQ before the trap frame is restored. If the queue is full, the handler still reads the byte and drops it. Leaving it in the hardware FIFO would keep the UART interrupt asserted, and the handler would run again as soon as `eoi` was written.

The consumer masks IRQs with `minemu_irq_disable`, copies one byte out, updates head and count, then calls `minemu_irq_enable`. The shell does this once per byte, then parses and prints with IRQs unmasked, so later keystrokes can still be queued. Masking is required because the handler and the shell are different execution contexts on the same core. Without it, the shell could read `count`, the handler could update `count`, head, and the buffer, and the shell could then pop a byte using a stale index.

The consumer does not sleep with `wfi`. A byte can arrive in the window after the empty check and before the wait instruction, and the echo test injects its line in one burst. A missed wake would leave that line sitting in the queue. The shell instead spins on the software queue. It is not polling the UART registers. The device interrupts when data arrives, and the handler moves those bytes into the queue.
